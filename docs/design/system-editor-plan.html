System Editor

You design the change on a live map of your system. Claude draws the map, questions your decision, then writes the code you approved.

Why

Approving AI output isn't the same as understanding it

Spec-driven agent workflows hand engineers thousands of lines of spec and diff to approve. Nobody has time to read them, so the approval becomes a skim. The engineer ends up verifying AI output instead of solving the problem, and the research suggests that's where skills erode.

17%

Lower comprehension scores for developers who learned a new library with AI help, in Anthropic's randomized trial. The speed gain wasn't statistically significant.

65–86%

Quiz scores for AI users with high-scoring interaction patterns, against 24–39% for low-scoring ones. How you use the AI matters more than whether you use it.

Strategic

The offloading that keeps the person thinking: AI as a thinking partner, with the person keeping agency. The opposite, habitual offloading, uses AI as a replacement.

The plugin builds the strategic pattern into the workflow. Claude does the tedious part (reading code to work out how it fits together), and the engineer does the part that builds judgment (deciding what should change and defending it).

The workflow

Same speed, different driver

Typical agent flow today

  1. YouAsk for a feature
  2. ClaudeWrites a long spec
  3. YouSkim and approve
  4. ClaudeImplements
  5. YouSkim the PR, LGTM
  6. ShipDeployed

Dashed steps are where understanding is supposed to happen and usually doesn't. Claude made every design decision.

With System Editor

  1. YouAsk for a feature
  2. ClaudeMaps the parts of the system it touches
  3. YouTrace the paths on the map, with code beside each step
  4. YouDraw the change: add, remove or reroute
  5. ClaudeQuestions the change: intent, failure modes, data
  6. YouAnswer and adjust
  7. ClaudePlans and implements only what you approved
  8. YouReview a PR mapped to your diagram

Outlined steps are your decisions. The map makes tracing fast, and nothing is built until you've drawn and defended the change.

How it works

One system model, passed between you and Claude

Everything hangs off a single file: a structured model of the system, generated from code, where every box and arrow links to the lines it came from. You read it in the editor and change it there. Claude grills you on your changes, builds from them, and checks the finished code against them.

What we build

The plugin, piece by piece

A Claude Code plugin bundles skills, subagents, hooks, MCP servers and a hooks module. A plugin with a hooks module is called a mod, and it can draw panes in the terminal and step into tool calls. Everything below ships as one plugin, sysedit.

PieceKindWhat it doesPhase
/sysedit:mapSkillReads the request, finds the entry points it touches, and writes .sysedit/model.json at three detail levels (services, modules, functions).0–1
mapperSubagent WorkflowOne mapper per entry point, run in parallel by a plugin workflow script. Each traces calls with the language server and records file and line evidence for every edge.0–1
.lsp.jsonLSPGo-to-definition and find-references, so edges come from the language server rather than text search. Reuse the official code intelligence plugins where they exist.0
sysedit serverMCP serverServes the editor on localhost and gives Claude tools: open_editor, get_model, get_change_set, record_answer.1
editorWeb appReact Flow canvas with Trace (step through a path, code beside it), Edit (add, remove, reroute) and Grill (answer questions) modes.1–3
/sysedit:grillSkill SubagentRuns on submit. A red-team subagent works through a rubric (intent mismatches, failure modes, timeouts, consistency, idempotency, events, security) and tags each question blocking or worth checking, with the code that prompted it.3
gateMod hookHolds Edit and Write outside .sysedit/ until the change set is approved with no open blocking questions. Can start as a PreToolUse settings hook script.3
/sysedit:planSkillTurns the approved change set and answers into an implementation plan, one task per operation, and refuses work that isn't on the map.4
/sysedit:verifySkillRe-maps the changed code and diffs it against the approved model. Reports drift: edges you drew that don't exist, and edges that appeared that you didn't draw.4
decision recordSkillWrites docs/adr/NNNN-*.md from your intent, diagram diff and answers, and a PR description that maps each file changed to a box on the diagram.4
status paneMod paneA pane in the terminal and the desktop Code tab: current stage, open questions, a button to open the editor. A band above the prompt shows what's blocking.2
/sysedit:skipSkillBypasses the process for small changes, logs the reason, and lets the gate through. Keeps the ceremony for changes that need it.5
Where the editor lives

Start in the browser, add native surfaces later

Mod panes only draw in the terminal and the desktop app's Code tab, and their elements are text, buttons and fields. A canvas you drag boxes around on needs a real web view, so the editor starts as a local web app and the mod handles status.

What makes it work

Five rules the build has to hold to

Every box has a source

No node or edge without a file and line behind it. Clicking anything opens the code. If engineers can't check the map, they won't trust it.

Say what was guessed

Dynamic dispatch, config routing and event buses get marked inferred, drawn differently, and offered as things to check rather than facts.

The diagram is the contract

Claude builds only what's on the approved map and verifies the result against it. Drift is reported, never silently accepted.

Questions earn their place

Every grill question cites the code that prompted it. A question you can't trace to evidence gets dropped. Blocking questions are rare and real.

Ceremony scales with risk

A typo fix skips the process. A change to a core flow gets all of it. Too much friction on small work gets the plugin turned off.

Roadmap

Six phases, each one usable on its own

Sizes are rough estimates for one engineer. Each phase ends with something a team can use, so you can stop or change direction at any point.

  1. 0~1–2 weeks

    Prove the map is right

    Everything depends on map accuracy, so test it before building any UI.

    Build

    • Model JSON schema
    • /sysedit:map skill and mapper subagent
    • LSP setup for one language
    • Render the model as Mermaid for checking

    Test on

    • 2–3 real repos the team knows well
    • 5 entry points each
    • Engineers mark each edge right, wrong or missing
    Exit when engineers who know the code agree the maps are accurate enough to trace from, and inferred edges are flagged rather than hidden.
  2. 1~2–3 weeks

    Trace mode

    A read-only editor that's useful on day one: onboarding, debugging, code review.

    Build

    • MCP server serving the editor locally
    • Canvas with entry-point picker and three detail levels
    • Step-through with code beside each step
    • Incremental re-map from git diff

    Ship as

    • Plugin loaded with --plugin-dir
    • Internal team marketplace
    Exit when engineers reach for it unprompted to understand unfamiliar code, and say tracing is faster than reading.
  3. 2~2 weeks

    Edit mode and change sets

    Engineers draw the change, and the editor records it as operations.

    Build

    • Add, remove and reroute tools, plus branches
    • Change-set file and intent note
    • Inspector for new nodes
    • Mod status pane and band above the prompt

    Watch for

    • Changes the canvas can't express
    • How long drawing takes compared with typing a prompt
    Exit when real feature requests can be expressed as change sets without falling back to prose.
  4. 3~2–3 weeks

    The grill and the gate

    Claude questions the change, and nothing gets written until the blocking questions are answered.

    Build

    • Red-team rubric skill and subagent
    • Evidence attached to every question
    • Answers that update the change set
    • Gate hook on Edit and Write

    Tune

    • Rate each question useful or noise
    • Cut rubric items that mostly produce noise
    Exit when engineers rate most blocking questions as catching something real, and the gate rarely gets bypassed.
  5. 4~2 weeks

    Plan, build, verify

    Close the loop from approved diagram to merged code.

    Build

    • /sysedit:plan constrained to the change set
    • /sysedit:verify drift check
    • Decision record and diagram-mapped PR description

    Then

    • Run verify in CI on PRs that carry a change set
    Exit when reviewers say the mapped PR is faster to review than a plain diff, and drift is caught before merge.
  6. 5ongoing

    Team rollout

    Make it the default path for changes that matter, and cheap to skip for those that don't.

    Build

    • Risk tiers and /sysedit:skip
    • More languages
    • MCP App version of the editor
    • Shared, versioned maps for the whole repo

    Distribute

    • Project-scope install via .claude/settings.json
    • Plugin evals in CI
    Exit when the metrics below hold up across several teams over a quarter.
Measuring it

How we'll know it's working

The claim has two halves: it keeps engineers' understanding intact, and it doesn't slow them down. Measure both, so the plugin can be judged on more than how it feels.

Map accuracyShare of sampled edges engineers confirm as correct. Tracked per language and per repo.
Time to first editFrom request to submitted change set, compared with writing a prompt and reading the spec.
Grill hit rateBlocking questions that led to a changed decision, divided by all blocking questions asked.
Drift caughtDifferences between approved and built model found before merge.
Post-merge defectsBugs and rework on changes that went through the process, compared with ones that skipped it.
Explain-backOccasionally, an engineer explains the flow they changed without the tool. A direct check on the original goal.

Risks and how we handle them

  • The map is wrong and engineers trace it with confidenceEvidence on every edge, inferred edges marked, and phase 0 accuracy checks before any UI.
  • The diagram becomes the new thing people skimThe engineer has to make the change on the map, so they must find where it fits. The grill asks about their specific decisions.
  • Too much ceremony, so people turn it offRisk tiers and a logged skip. Measure the skip rate and treat a high one as a design problem.
  • Mapping costs too many tokens on large reposMap only the entry points the request touches, cache by commit, and re-map incrementally from the diff.
  • Some changes don't fit boxes and arrowsAllow a prose note on any node or edge. Track what couldn't be drawn and extend the operations to cover it.
